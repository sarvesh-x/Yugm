# 2026-11-24 — D1 wallet routes and payments

## Scope

Port the six remaining `/api/wallet` patterns to the local MongoDB-free D1 Worker and keep the wallet ledger, purchases and VIP entitlements authoritative in D1. MongoDB remains authoritative for the deployed legacy runtime until route/job parity, reconciliation, recovery rehearsal and live acceptance pass. Work stayed on `master`; all pre-existing staged/unstaged changes and untracked files were preserved. No commit, push, deploy, provision, hosted migration, credential rotation or production data operation was performed.

## Changes applied

- Added the six missing routes in `backend-server/apps/api/src/migration/d1Wallet.ts` and mounted the wallet router in `d1App.ts`. All 16 audited `/api/wallet` method/path patterns are now mounted: purchase history, Razorpay order creation, Razorpay verification, Google Play verification, VIP activation and dev recharge.
- Added `backend-server/apps/api/src/migration/d1Payments.ts`: host-neutral Razorpay order/fetch/signature and Google Play verify/consume calls plus Web Crypto HS256 JWT and escaped-PEM RSA signing helpers. No Node-only payment SDK or native library is reachable from the Worker.
- Forwarded `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `GOOGLE_PLAY_PACKAGE_NAME`, `GOOGLE_PLAY_CLIENT_EMAIL` and `GOOGLE_PLAY_PRIVATE_KEY` from `D1ApiEnv` into `createD1App`. Provider calls are injected, and Razorpay/Google Play are stubbed by outbound mocks in the local fixture. No live provider call was made.
- `POST /api/wallet/dev-recharge` is enabled only when `YUGM_STAGE=local`; hosted stages return 404. Amount parsing, floor, 25,000 cap, default 500 and `RECHARGE` source follow the legacy route.
- Razorpay verification rechecks the actor-scoped order, HMAC, fetched payment order/amount/currency/status and credits once. Google Play verification checks product/package, cross-user token reuse, purchase state and ownership, credits once and consumes only after the authoritative credit.
- VIP activation keeps the debit, VIP fields, guarded XP grant and cap counter in one D1 batch. The ledger insert precedes the purchase/debit claim so D1 foreign keys are satisfied. Reused wallet helpers exported from `d1Cosmetics.ts` and added purchase/diamond schema checks in `d1Api.ts`.
- Added `backend-server/apps/api/migrations/d1/0008_wallet_purchase_indexes.sql` and wired it into the auth and production local fixtures.
- Fixture-driven fixes: ledger rows must exist before purchase rows that reference them; the batch order is ledger → claim → user update; the invalid-order case needs a distinct fixture order ID.

## Not run / still open

- Hosted migrations `0003`–`0008`, live FCM delivery, live Android/Firebase and RTC acceptance, deployed endpoint smoke, data import, reconciliation and cutover.
- Production/staging payment values and secrets (`RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `GOOGLE_PLAY_PACKAGE_NAME`, `GOOGLE_PLAY_CLIENT_EMAIL`, `GOOGLE_PLAY_PRIVATE_KEY`) are not configured in the tracked production config; they require owner-supplied secrets before live purchases can work. Provider calls were mocked only.
- Legacy grants VIP XP as a non-fatal post-commit side effect (`runWalletSideEffect`); D1 stages the guarded XP grant in the same debit batch, matching the existing cosmetic-purchase flow. An XP overflow/constraint failure therefore rejects the VIP purchase instead of silently granting VIP without XP. This atomicity choice is deliberate but needs owner review before cutover.
- `xp_grants` receipts are always inserted by `prepareD1XpGrant()`, even when `xpAwarded` is 0, whereas legacy skips the receipt for a zero/capped grant. Guard behavior and cap counters are otherwise preserved.
- D1 still has no `bonds:changed`, `sync:invalidate` or `notification:new` emitter; receiving-client realtime stays staged/hybrid.
- Admin, moderation and account-deletion routes and the remaining `/api/rooms` patterns are not mounted on D1. Weekly honors, 30-day account deletion, 48-hour stale-room cleanup, `runPkDeadlines`, Socket.IO presence/grace/fan-out/cache paths and PK routes remain on the legacy runtime.
- Production/staging `YUGM_BONDS_ENABLED` values remain unconfirmed, and the original release Google 409 root cause is still unconfirmed.
