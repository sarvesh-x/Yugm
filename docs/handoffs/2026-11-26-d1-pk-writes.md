## Behavior preserved

- Router-scoped authentication runs before path/body validation on all four routes, matching legacy `pkRouter.use(requireAuth)`. The PK surface has no rate limiter, so none was added.
- `room-start` keeps the legacy schema and validation order: muted check before body validation, player-selection/team/duration rules, LIVE-room and manager checks, restricted-manager message, active mic-seat check and gift availability/points checks. The retained messages include `Room must be live to start a PK` and `Restricted room managers cannot start PK`.
- `reject` keeps invite lookup, invitee-only authorization, pending check, expired-invite recovery, then the invite/battle transition and `PK_INVITE_REJECTED` event. Replays return the legacy conflict messages.
- `cancel` keeps the cancellable-status set, cross-room manager check versus in-room host/starter check, `CANCELLED` transition, invite cancellation, `PK_CANCELLED` event and room-lock release. Non-cancellable active battles get the legacy `An active PK must be ended, not cancelled` conflict.
- `close` validates `battleId`, then checks room/host/admin authorization before the `CLOSED` and status checks, matching legacy. It preserves `Invalid battleId`, `Only a room host or admin can close PK`, and `Finalize or cancel PK before closing it`. A replay on an already `CLOSED` battle returns the current battle instead of writing again.
- Battle status changes increment `state_version`; HTTP responses use the `sendOk` envelope and the existing D1 PK battle presenter from the read slice. No route reports success before its D1 batch commits.

## D1 implementation

- Added `backend-server/apps/api/src/migration/d1PkWrites.ts` and mounted it in `d1App.ts` immediately after `createD1PkReadsRouter(db)` at `/api/pk`.
- Used conditional CTE inserts/updates inside `db.batch(...)` for the room lock, battle/invite transitions and event rows. D1 lacks the legacy unique indexes and `batch` does not roll back on a manual post-commit validation failure, so guards are part of the writes rather than checks after commit.
- `room-start` inserts the battle, participants and `PK_CREATED` event only when the room has no `active_pk_id`; the final room-lock update is the commit indicator. Reject, cancel, expiry and close release locks only when the room still points at that battle.
- Event inserts are guarded by the committed target state so replayed POSTs do not duplicate `PK_INVITE_REJECTED`, `PK_CANCELLED` or `PK_CLOSED`. Rejecting an expired invite follows the existing expiry helper and writes `PK_INVITE_EXPIRED`.
- No new migration. Existing `pk_battles`, `pk_invites`, `pk_events`, `pk_participants`, `rooms` and `users` tables are used unchanged. `randomBytes` from `node:crypto` follows the established D1 helper pattern for battle codes.

## Boundaries and divergence

- This is HTTP-only. The acting client can apply the response or clear local PK state, but other room participants need a refresh through `GET /api/pk/active/:roomId`. No `pk:state`, `pk:ended`, `pk:invite:*` or `notification:new` emit exists on the Worker.
- Invite, accept, start, ready, vote, send-gift, reactions, rematch and end writes remain legacy-only. Wallet debit, gift transaction linkage and vote/participant/leaderboard uniqueness need explicit D1 handling before those writes are mounted.
- D1 has no PK deadline recovery: legacy timers are disabled in the Cloudflare runtime, D1 Cron does not call `runPkDeadlines()`, and `endD1Room()` does not end active PK battles. Battles left in `PREPARING`/`COUNTDOWN`/`ACTIVE` need that boundary closed before cutover.
- Legacy DDL lacks unique indexes for `battle_code`, votes, participants, leaderboard pairs and event sequence; imported data needs duplicate audits. D1 `pk_battles.status` CHECK also rejects `OVERTIME`, which the legacy state machine reads. This slice never writes `OVERTIME`.
- Battle DTOs use the existing host-neutral presenter, so the HTTP shape is consistent with the PK read routes. The legacy `emitPkState()` socket projection is not produced here. Deterministic D1 ordering may differ where MongoDB left ordering undefined.
