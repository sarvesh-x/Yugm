# Local D1 and R2 app expansion

The owner expanded local debug from Auth and Profile to the whole Android app and admin workflows. The baseline was clean at `05617d2`. The acceptance target is one loopback Worker using D1 for app records and R2 for managed file bytes, with no MongoDB service needed for supported debug journeys. Preserve the existing Android HTTP contracts, commit authoritative writes before reporting success, and exercise cross-account behavior with separate sessions.

## What runs locally

- **Auth, Profile and avatars.** The existing `auth-local` Worker verifies Firebase identity, issues D1-backed Yugm sessions, reads and writes profiles, and uses its five local R2 bindings for managed avatars. The standard Android debug emulator points to the Worker when it is run on port 4000.
- **Player cosmetics.** The existing Android wallet, catalog, full inventory, single and bundle purchase, equip, unequip and transfer endpoints now run on local D1. The default catalog comes from the same shared definitions as the Node API. Seeding preserves edited rows. Owned reward and inactive inventory visibility follow the existing read paths. The full inventory also reads gift and achievement ownership rows from D1.
- **Published cosmetic art.** A matching published D1 asset resolves to a Worker URL which reads the recorded variant from local `ASSETS` R2. Staged, archived and unregistered variants are unavailable. Older catalog art can still reference external URLs. Admin upload, publication, archive and catalog editing require their own D1-backed authorization and write paths.
- **Cosmetic mutations.** A D1 batch commits the debit with ownership, auto-equip for single items, capped XP, Battle Pass progression and any level reward. A failed grant rolls the purchase back. Concurrent repeats of a single purchase observe existing ownership. Bundle retries return the existing all-owned conflict. Transfers move ownership and persist a recipient inbox row in one batch. The local route rejects self-transfers and duplicates to a recipient who already owns the item. It clears the sender's equipped slot only when the transferred item occupies that slot.
- **Clan membership.** D1 serves clan discovery, current membership, detail and public rankings. Creation, public joins, settings, ownership transfer, leaving, and the send, list, cancel, decline and accept invitation paths keep membership, roles and the user profile pointer consistent. The worker enforces private-clan visibility, invite and settings permissions, active-session checks on mutations and one current clan per user. Leaving an empty clan removes its child records. Clan invitations write a recipient inbox row. Existing avatar URLs remain supported. Clan media upload, presence, app event delivery, member role changes, kicks, explicit disband and clan chat are still open.
- **Notification inbox.** D1 serves account-scoped inbox items, unread counts, mark-read, read-all and click tracking. The recipient can load a cosmetic gift or clan invitation using the same API Android calls. Socket and FCM delivery are separate paths.

## Remaining runtime dependencies

| Journey | Current path and next implementation |
| --- | --- |
| Settings, Discover, friendships and direct messages | Their normal routes still use MongoDB. Port privacy, blocks, friends and device-token registration on the shared D1 session boundary. Use the existing mounted direct-message characterization for history, receipts, mute, block and retries. |
| Voice and video rooms | `rooms.ts` reads and writes MongoDB room state, seats, invitations, activity and entitlements. `livekit.ts` reads the active participant to authorize publishing and subscribing. Android's `RoomApi` requests those tokens, `YugmMediaRoom` handles media, and `RoomSocketClient` handles app events. Move room and participant persistence to D1, test authorization on token issuance, and verify join, leave, role changes and reconnects on two clients. R2 can hold covers and recordings. Live audio and video require a separate WebRTC provider, such as local LiveKit with the current Android client. [Cloudflare Realtime SFU architecture](https://developers.cloudflare.com/realtime/sfu/) |
| Bonds | `bonds.ts` and `bonds.js` use MongoDB for availability, eligibility, profile privacy, active slots, requests, gifts, wallet holds, points, rewards and ranking. Profile reads already consume D1 bond relationship counts. Port the dedicated read routes and transactional write workflows, including expiry, cancellation, holds and notification fan-out, before switching the Bonds UI. |
| Admin, media and moderation | Admin sessions, role checks, audit logs and asset routes still rely on the standard API. Managed avatar is the only local upload category. Port each category with ownership, visibility, quota and cleanup, then migrate room and clan avatars, stories, chat attachments, moderation evidence, recordings and remaining legacy asset references. |
| Economy, progression and other features | The cosmetic portion of the wallet is local. Gift sends and trades, check-in, wallet history and reward claims, payments, subscriptions, games, events, creator flows and scheduled maintenance still need their own D1 work. The existing Arcade catalog fixture demonstrates an injectable D1 read contract. |
| Runtime and realtime | The standard Worker calls `connectDatabase`, starts Socket.IO and initializes Mongo-backed indexes, storage and jobs. The local Worker rejects MongoDB and Redis bindings. Its bundle still carries Mongoose through shared auth/model hydration and legacy imports. Remove those imports after equivalent validators and serializers pass parity checks. Wire local app events and scoped replay using the existing Durable Object and compatibility work. |

The D1 schema already contains normalized tables for the requested domains. Table presence shows the data model exists. An HTTP route, service, job or socket handler must use those tables before the app can exercise that behavior locally. Staging and production continue on the existing deployment configuration. Production MongoDB retirement requires a separate capacity and recovery decision under [ADR-0007](../decisions/0007-dcr2-capacity-gate-not-approved.md).
