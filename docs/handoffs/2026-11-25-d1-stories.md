# 2026-11-25 — D1 story routes

## Scope

Mounted all 11 `/api/stories` patterns on the shared D1 Worker, extending the existing story-comment deletion router rather than adding a second router:

- `POST /api/stories`
- `GET /api/stories/feed`
- `GET /api/stories/user/:userId`
- `POST /api/stories/:storyId/view`
- `POST /api/stories/:storyId/like`
- `POST /api/stories/:storyId/hide`
- `DELETE /api/stories/:storyId`
- `GET /api/stories/:storyId/views`
- `POST /api/stories/:storyId/comments`
- `GET /api/stories/:storyId/comments`
- `POST /api/stories/:storyId/comments/:commentId/reply`

MongoDB remains authoritative. No hosted migration, data import, deploy, provision, credential change, commit or push was performed for this slice.

## Characterization

A disposable local MongoDB fixture exercised the legacy Express app before any D1 change and was then deleted. It confirmed:

- create returns the raw story with `userId` as a string, trimmed `caption`, `viewedBy: []`, `likeCount: 0`, `replyCount: 0`, 24-hour `expiresAt`, `status: "ACTIVE"`, `_id` after mutable fields, timestamps and `__v: 0`;
- feed groups active unexpired self/following stories by user ID and returns each populated author with only `name`, `username`, `avatar`, `avatarType` and present `avatarParts` keys;
- user stories use the same populated DTO with legacy skip/limit behavior;
- repeat views are idempotent and views return populated viewers in insertion order;
- likes increment on every call, hide and delete are owner-only, and `views` reads the story before returning viewers;
- comments trim `text`, increment `replyCount`, notify the story owner unless the actor is the owner, list roots newest-first with replies oldest-first, and reply notifications go to the comment parent;
- legacy story deletion leaves story comments and highlight references dangling, and legacy comment deletion leaves replies orphaned because its `deleteMany({ _id, parentId: _id })` cannot match a child.

## D1 implementation

- `backend-server/apps/api/src/migration/d1Stories.ts` now owns all story routes plus the existing `DELETE /api/comments/:commentId`. Each route calls `requireHttpSession` explicitly so unrelated `/api` routes are not intercepted.
- `POST /stories` checks auth, then `enforceD1UserRateLimit(limits.create, userId, res, 60)`, then body validation, matching the legacy `requireAuth → createLimiter → validateBody` order. Validation accepts the legacy media types, optional styling fields, URL-or-empty `linkUrl`, duration 1–300 and length limits.
- Story creation commits the story and every follower `MOMENT` notification in one D1 batch using the current user name from `users`. Notification delivery remains the existing D1 push-job trigger; no Socket.IO `notification:new` emitter exists on this Worker.
- Feed/user reads use a compact populated-user JSON projection that omits absent nullable fields and partial `avatarParts`, while raw story documents retain `__v: 0` and field order.
- Views, likes, hides, comments, replies and comment deletion use guarded D1 statements/batches. Views replay against `(stories_id, value)` before insert; `0028_story_views_unique.sql` closes the concurrent duplicate race in fresh fixtures.
- Comment and reply writes commit the row, `reply_count` increment and notification together. `DELETE /comments/:commentId` still removes the whole descendant thread required by the self-referencing D1 key and decrements `reply_count` by the number removed.
- `DELETE /stories/:storyId` removes dependent comment, highlight and view rows with the story because D1 enforces their foreign keys. Legacy left those rows dangling; the visible HTTP contract is unchanged, but the D1 database does not retain orphaned dependents.
