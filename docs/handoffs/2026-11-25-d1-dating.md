# D1 dating routes

The shared D1 Worker now mounts five of the six legacy `/api/dating` HTTP patterns: preference read/update, like, pass and match listing. `GET /api/dating/explore` deliberately stays on the legacy Socket.IO/Redis path because its `onlineOnly` filter and `isOnline` field are derived from live socket presence, not durable D1 state. The audit reports `/api/dating` as `5 mounted / 1 missing`; overall coverage is `legacy 638 / d1 275 / matched 270 / missing 368`.

## Behavior preserved

- `GET/PUT /api/dating/preferences` keep the legacy auth-before-validation order, field defaults, parsed-body response and relaxed validation on the second request. The guarded preference write revalidates the live D1 session before committing.
- `POST /api/dating/like` keeps the legacy order: shadow-ban check, `likedId` validation, self-like rejection, block guard, swipe replay, then the `type` enum error produced by Mongoose. Replay returns `400 "Already swiped on this user"`.
- A mutual non-`PASS` like creates one match with the legacy 50 XP, or 75 XP for a super-like match. Relationship XP, level-up and seven-day streak notifications, match creation, both match members and the two “It's a Yugm!” notifications commit in one guarded D1 batch. Stale relationship state is guarded rather than overwritten.
- `POST /api/dating/pass` keeps its distinct `Invalid user ID` message, shadow-ban check and replay behavior, and stores `PASS` in the same `likes` table.
- `GET /api/dating/matches` lazily creates relationships for older matches, preserves the populated partner DTO and VIP fields, and keeps both `id` and `_id` in match and partner projections.

`0025_dating_swipes.sql` adds the swipe-pair, liked/type, relationship-pair, match-member and match timestamp indexes plus a nullable `matches.pair_key`. These keys make concurrent duplicate swipes and matches fail closed in fresh D1 databases. The migration is added to the fresh Worker fixture sequence only; hosted application still needs a duplicate audit of legacy `likes`, `relationships`, `relationship_users` and `match_users` rows first.

## Boundary and remaining work

`GET /api/dating/explore` remains legacy-only. Replacing Redis/Socket.IO presence with a D1 auth-session proxy would change the meaning of `onlineOnly` and `isOnline`; this slice does not claim that parity. Mounting it requires an authoritative presence source or an explicitly approved compatibility decision.

`0025` is not applied to the recovered local `yugm` database, which remains at `0019`, or to hosted D1. MongoDB remains authoritative. No provision, hosted migration, data import, deploy, credential change, commit, push or MongoDB retirement was performed. Live FCM delivery, two-client Android acceptance and deployed dating-journey verification remain open.
