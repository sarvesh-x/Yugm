# D1 missions routes

## Scope

Mounted all four legacy `/api/missions` HTTP patterns on the shared D1 Worker on 2026-11-25. MongoDB remains authoritative. No deploy, hosted migration, seed or hosted data operation was performed.

| Route | Behavior |
| --- | --- |
| `GET /api/missions` | Active catalog with optional `type` filter; lazily seeds when no active mission exists. |
| `GET /api/missions/active` | Active, date-windowed missions grouped by type with user progress, completion and claim state. |
| `POST /api/missions/progress` | Upserts progress for matching active missions and marks completion at the target. |
| `POST /api/missions/claim` | Checks completion and claim state, then grants XP and coins under one guarded D1 batch. |

The audit now reports `legacy 638 / d1 246 / matched 241 / missing 397`, with `/api/missions` at `4 mounted / 0 missing`.

## Behavior notes

- **Seed ownership.** The catalog was moved from `models/Mission.ts` to a host-neutral `src/data/missionSeeds.ts`. The Mongoose model re-exports it, so the legacy import path is unchanged and the Worker bundle never imports Mongoose for mission seeds. As in the legacy route, seeding runs only when no active mission exists; a single active row prevents seeding.
- **Two different active definitions.** `GET /api/missions` filters only on `active = 1`, while `GET /api/missions/active` also applies the `startDate`/`endDate` window. Both were preserved, including dates that make a mission invisible to the grouped route but visible in the catalog.
- **Progress.** Upsert uses the `(user_id, mission_id)` key added by `0021_user_mission_unique.sql`. Stored progress keeps the raw increment; the response caps it at the mission target and reports completion when the capped value reaches the target. Completion is set in the same batch.
- **Claim.** The legacy handler grants XP before opening its coin transaction. D1 stages the XP grant, level/battle-pass effects, coin ledger row, wallet update and claim flag in one atomic batch under a scratch `user_auth_profile.edit_token` claim. `xp_grants` keeps the legacy `mission:<userId>:<missionId>` action key and the coin ledger uses the `:coins` suffix. An existing XP grant with that action key returns `409` rather than creating a duplicate receipt.
- **Rewards.** Only XP and coins are returned and credited, matching the legacy handler. Diamond rewards in the mission document remain uncredited, as in the legacy service.
- **Validation order.** Authentication runs before Zod validation, then the mission ID object-id check, then mission existence, completion and claim state.
