# Cloudflare free-plan migration audit

Status: **experimental; not ready for real user data or production**. A Worker and Pages admin have been deployed to isolated staging. The staging database was empty before startup; the Worker created indexes and default records. No production database, object store, DNS record, webhook, or production traffic has been changed. The hosting target is Cloudflare Workers and Pages. There is no upstream proxy to the old host and no container service.

- Staging API: `https://yugm-api-staging.sarveshkumar10101.workers.dev`
- Staging admin: `https://yugm-admin-staging.pages.dev`
- A staging-only admin account is configured and its credentials are in an ignored local file. The active Worker has credentials for the separate Yugm Staging Project on LiveKit's free Build plan.
- Two disposable accounts used the staging API to create and join voice and video rooms. The audience received synthetic audio in the voice room and both audio and video in the video room. Host closure delivered the Socket.IO event, removed the active participant records, disconnected both LiveKit clients, and rejected subsequent media token requests. Android device testing is still pending.
- Remote smoke checks passed for health, Socket.IO authentication and room join, user events, media upload/download, PK countdown/completion, room closure and admin login with disposable test records. The Pages entry and restricted API CORS preflight passed. One longer room-close test timed out before two subsequent runs passed; investigate timing and load before cutover.

## What exists today

The API is Express and Mongoose with Socket.IO, local process state, scheduled maintenance, and PK timers. The Android clients force Socket.IO's WebSocket transport. Voice and video media depend on a separate LiveKit service. The admin app is a Vite SPA. The production database plan, data size, backups, LiveKit plan and media inventory have not been verified.

The API exposes authentication, profiles, rooms, chat, notifications, PK, gifts, wallets, purchases, admin, uploads and many other endpoints. Wallet, gifts, PK and related paths use MongoDB transactions; a replacement database must preserve transaction semantics and existing identifiers. A simple export to D1 or a change of database without a tested migration would not preserve these guarantees.

## Compatibility gates

| Area | Current finding and work required |
| --- | --- |
| Worker bootstrap | Local Wrangler and the deployed staging Worker returned HTTP 200 from `/health` after connecting to isolated MongoDB databases. Selected authentication and API paths passed staging smoke checks; full contract coverage and resource limits remain unverified. |
| MongoDB | Cloudflare documents Mongoose 9+ with Node compatibility. Upgrading this API directly to Mongoose 9 produced hundreds of TypeScript errors; the existing version remains in place. Confirm a supported Worker entry point and test all data and transaction behavior before a version change. [Cloudflare MongoDB guidance](https://developers.cloudflare.com/workers/databases/third-party-integrations/mongodb/). |
| Realtime | The Node HTTP compatibility layer does not support HTTP upgrade events. The experimental Worker accepts WebSocket upgrades and hands them to the existing Engine.IO server, retaining its Socket.IO handlers. Local and staging tests verified authentication, room join acknowledgements, user events and room broadcasts; a local test verified heartbeat and reconnect during the disconnect grace period. One staging room-close event timed out in a longer run, followed by two passing runs. Production readiness still requires diagnosing that timeout, Android clients, process-restart recovery, concurrent room load and free-tier measurements. The bridge relies on Engine.IO internals and must be retested whenever dependencies change. [HTTP compatibility](https://developers.cloudflare.com/workers/runtime-apis/nodejs/http/). |
| Process lifetime | The Worker schedules PK countdown, ticking, completion, invite expiration and result closure from persisted MongoDB deadlines using Durable Object alarms. A local integration test verifies a battle completes after a Worker restart and that a result closes on an alarm. Disconnect grace periods and presence still use process timers and in-memory state; restart recovery, multi-user PK concurrency and room close behavior need further testing and work. |
| Media | The staging Worker stores new uploads in MongoDB GridFS and uses request-scoped temporary files. A local integration test covers upload, public retrieval, byte ranges, owner-only verification access and persistence after restart. Worker uploads are currently capped at 10 MiB; the existing Node API permits recordings up to 200 MiB. A chunked upload design, old URL mapping, content reconciliation and capacity monitoring are required before cutover. Existing missing `/uploads` files cannot be reconstructed from database references alone. |
| R2 cost | R2 includes a free allowance but requires subscription checkout and bills for usage above that allowance. It is **not provisioned**. MongoDB GridFS is the experimental storage target; it shares the free database's 0.5 GB capacity with users, messages, wallets and indexes. The prototype reserves media bytes atomically against a configurable 128 MiB default quota; this does not cap total database usage. A crash can leave an unused reservation, requiring a carefully coordinated reconciliation. Verify actual database size and monitor the remaining capacity before production. [R2 setup](https://developers.cloudflare.com/r2/get-started/) and [pricing](https://developers.cloudflare.com/r2/pricing/). |
| Push, moderation, media | LiveKit token issuance, role-based publishing permissions and media delivery passed staging SDK checks. Firebase Admin, App Check, push delivery and TensorFlow moderation still need Workers tests. |
| Background work | The 15-minute maintenance job performs deletions and room cleanup; it must run only against the intended database, recover after interruptions and be checked for duplicate work. PK deadline processing uses alarms in the Worker and should be load tested under simultaneous battles and interrupted finalization. |
| Operations | Startup currently creates indexes, runs migrations and seeds official data. Do not run it against production until a backup, migration review and rollback procedure are verified. Never put secrets in source control or logs. |

Cloudflare's Workers Free plan currently allows 100,000 requests per day and 10 ms CPU per HTTP invocation; requests fail after the account limit is exhausted. Durable Objects have their own free limits. Polling generates recurring requests for every connected user and therefore needs measured load testing and a clear capacity limit. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [Durable Objects pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/).

The installed Socket.IO Android client uses Engine.IO 4, WebSocket transport and a room-join acknowledgement. The bridge retains the existing event handlers, but it uses regular, non-hibernating WebSockets and process-local state; connections and state must recover after a Worker restart. Measure Durable Object active duration, connection handling and the impact of heartbeats against the free quota before depending on it. The [Engine.IO protocol](https://socket.io/docs/v4/engine-io-protocol/) and [Durable Object WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/) describe the required mechanics.

MongoDB Atlas has a free cluster with a 0.5 GB data limit and other throughput limits, but the current database provider, size and plan are unknown. Do not migrate data into a free cluster until its size, indexes, transactions, backups and restore have been checked. [Atlas limits](https://www.mongodb.com/docs/atlas/reference/free-shared-limitations/).

LiveKit Cloud's free Build plan has hard caps, including a default concurrency limit of 100 participants. Free projects under the same user share their allowances. Confirm the production project's plan and measure real usage before relying on the free media service. [LiveKit quotas](https://docs.livekit.io/deploy/admin/quotas-and-limits/).

## Release sequence

1. Use the separate staging MongoDB database, LiveKit project, staging secrets and Pages CORS origin already configured. Verify that the credentials in any local secrets file match these staging resources before uploading the file to Cloudflare.
2. Finish the compatibility gates above. Validate local Worker startup, authentication, rooms, realtime reconnect, chat, gift and wallet transactions, media access, PK recovery, push, maintenance and rollback using staging-only data. Measure free-tier usage under realistic concurrency.
3. Build and deploy the admin SPA on Pages with a staging API origin. Verify login, authorization, uploads and deep links. The Pages build configuration is documented alongside the Pages workflow.
4. Inventory and back up all database collections and media, verify a restore, reconcile copied objects and validate the existing media URLs. Plan how old Android releases reach the new endpoint; updating a URL in the next app release alone does not migrate installed clients.
5. Only after staging passes, prepare a reviewed production deployment with the existing persistent JWT and encryption secrets, the correct MongoDB and service credentials, separate production resources, explicit origins and verified rollback. The migration request requires explicit production cutover approval before DNS or traffic changes.

Pushes to `master` deploy only to Cloudflare staging. The legacy Render Blueprint is retained for rollback with its automatic deploy trigger disabled. Android release/production builds now default to the Cloudflare staging Worker (`https://yugm-api-staging.sarveshkumar10101.workers.dev`) and its staging Pages admin (`https://yugm-admin-staging.pages.dev`); the Worker's production startup guard remains in place until production cutover is authorized.
